# Contributing to the State Operating System (SOS)

Thank you for contributing to Nigeria's unified subnational digital governance platform. SOS is engineered under strict public-procurement, data-sovereignty and open-source governance rules. This document defines how to contribute safely.

## Ground Rules

1. **Canonical Core, Dynamic Policy Packs.** Never hard-code state-specific tax rates, fee schedules, concession splits, or workflow stages into application binaries. State variation belongs in `config/states/<state>/` policy packs (JSON/OPA Rego). Anything beyond the **80/20 rule** (≥80% shared configuration) is a product-management escalation, not a professional-services order.
2. **Provenance tagging.** Every material data point in documentation or config must carry `[LIVE]`, `[DERIVED]`, or `[GAP]`. Derived figures are negotiating starting points — never present them as sourced findings.
3. **Double-entry correctness.** All monetary movement goes through the TigerBeetle ledger (`ledger/`). SQL `UPDATE balance` patterns are prohibited (ADR-002).
4. **Tenant isolation is non-negotiable.** All new tables carrying state data must include `tenant_state_id` and PostgreSQL Row-Level Security policies (see `db/migrations/`).
5. **Open contracts.** All microservices must expose documented REST/gRPC APIs compliant with OpenAPI 3.1 (`contracts/openapi/`) and events via AsyncAPI (`contracts/asyncapi/`).

## License & SBOM Policy

- The SOS core is **Apache-2.0**. Dependencies may only use permissive licenses: **MIT, Apache-2.0, BSD 2/3-Clause, ISC, PostgreSQL License**.
- Copyleft licenses (GPLv2, GPLv3, AGPLv3) require explicit written approval from the State Attorney General before introduction.
- Every release must ship a cryptographically signed **SBOM** conforming to CycloneDX v1.5 or SPDX v2.3 (generated by CI: `.github/workflows/sbom.yml`).

## Development Workflow

1. Fork / branch from `main`. Branch naming: `feat/<module>-<short-desc>`, `fix/<issue-id>-<short-desc>`, `config/<state>-<policy-change>`.
2. All changes via Pull Request. PRs must include: linked issue/work-package reference (WP-xx), test evidence, and updated contract/docs where applicable.
3. CI must pass: build, unit tests (>85% coverage for new code), OpenAPI schema validation, container vulnerability scan, license/SBOM check.
4. Approvals per `CODEOWNERS`: ledger and settlement code requires **2 approvals** including a Core Financial pod maintainer.
5. No secrets, tokens, or credentials in the repository. Use OpenBao/Vault patterns referenced in `infra/`.

## Acceptance & Testing Gates

Contributions land inside the five-stage acceptance lifecycle (FAT → Performance/Stress → Security/Pen-Test → SAT → UAT). Load-test scripts live in `tests/` and map to procurement gate metrics (e.g., 500k TPS TigerBeetle, 50k req/s APISIX, 10k concurrent Sedona spatial joins).

## Code of Conduct

Be professional, evidence-driven, and respectful. This platform handles sovereign citizen data — treat privacy, auditability, and institutional trust as first-class engineering requirements.
